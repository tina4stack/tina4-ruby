# Releasing tina4-ruby

Releases are cut on a dedicated `feature/release<version>` branch, merged into
`v3`, then **tagged**. The tag (matching `[0-9]*.*.*`, e.g. `3.13.121`) is what
triggers the RubyGems publish workflow -- merging alone never publishes, the tag
does. So the tag is the point of no return: whatever the version-bearing files
say at the tagged commit is what ships.

## Version-bearing files

The release version is stamped in these files, which MUST all agree before a tag:

| File | Where |
| --- | --- |
| `lib/tina4/version.rb` | `VERSION = "X"` -- the canonical source of truth |
| `CLAUDE.md` | header line `Version X - TINA4...` |
| `CLAUDE.md` | footer line `- Version: X` |
| `Gemfile.lock` | `tina4ruby (X)` -- regenerated by `bundle install` |

`tina4.gemspec` and `tina4ruby.gemspec` do **not** hardcode the version: both
`require_relative "lib/tina4/version"` and set `spec.version = Tina4::VERSION`,
so they follow `version.rb` automatically and cannot drift.

## Pre-tag checklist

Run these IN ORDER on the release branch, before `git tag`:

1. Bump the version in `lib/tina4/version.rb` and BOTH `CLAUDE.md` lines to
   `3.13.NNN`.

2. Regenerate the lockfile so `Gemfile.lock` picks up the new version (the
   manifest and lock ship together):

   ```bash
   bundle install
   ```

3. **Assert every version-bearing file agrees -- BEFORE the tag, not on CI
   after:**

   ```bash
   ruby scripts/check_version_consistency.rb 3.13.NNN
   ```

   Exit 0 = every stamp agrees. Non-zero = the script names each file left
   behind by a partial bump and its stale value. Fix them and re-run until it is
   green.

4. Run the full suite green at the exact HEAD you are about to tag:

   ```bash
   bundle exec rspec
   ```

5. Only now tag and push:

   ```bash
   git tag 3.13.NNN
   git push origin 3.13.NNN
   ```

The consistency check is intentionally left of the tag: a drift caught here
costs a re-run; a drift caught on CI costs a pushed tag that already ran ahead of
the version-bearing files. `spec/version_consistency_check_spec.rb` also runs the
same check on every `bundle exec rspec`, so a self-inconsistent HEAD fails the
suite before it can ever be tagged.
